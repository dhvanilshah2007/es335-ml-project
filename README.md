## 1. Project Overview & Research Question

This project investigates whether multivariate sensor telemetry from jet engines can reliably forecast impending failure early enough to outperform a **fixed-interval replacement schedule**. 

Instead of treating accuracy as the sole criterion, this project frames machine learning around operational decision-making:
- **Core Research Question:** *Can trailing sensor history up to operational cycle $t$ predict remaining useful life ($RUL$) and trigger an alarm ($\text{RUL} \le w$) early enough to beat a fixed maintenance schedule under realistic cost trade-offs?*
- **The Decision Problem:** In rotating machinery, running to failure causes catastrophic downtime and safety hazards ($c_{\text{fail}}$), while premature replacement discards valuable remaining life ($c_{\text{waste}}$). We compare a model-triggered replacement policy against the best fixed-cycle schedule ($K$ cycles) across multiple cost ratios ($c_{\text{fail}} : c_{\text{waste}}$) and locate the break-even point.

> **Important Domain Context:** The NASA C-MAPSS data is generated by an engine simulator (single operating condition, high-pressure compressor degradation). It is cleaner than real fleets (no missing values, no censoring, known wear parameters). We treat this strictly as a benchmark study without claiming causal failure attribution or real-world flight deployment readiness.

## 2. Problem Formulation

| Element | Definition |
| :--- | :--- |
| **Unit of Observation** | Single engine (`unit_id`) at cycle $t$, using features computed over trailing window $[t-k+1, t]$ |
| **Input Information** | Cycle count (age), 3 operational settings, and 21 sensor streams up to cycle $t$ (strictly trailing) |
| **Primary Targets** | **(a) Continuous RUL:** Remaining cycles to failure, capped at 125 cycles (early degradation is unobservable)<br>**(b) Binary Alarm:** $1$ if $\text{RUL} \le w$ cycles ($w=30$ cycles default; sensitivity tests at 15 and 50) |
| **Prediction Timing** | End of cycle $t$, without future cycle leakage |
| **Decision Policy** | Replace engine at the first cycle where the model alarms, or at cycle $K$ under a fixed schedule |

## 3. Methodological Rigor & Evaluation Ladder

### Leakage-Proof Splitting
- **Engine-Level Grouping:** We split the 100 training engines into **80 development engines** and **20 held-out test engines** using a fixed random seed.
- **Cross-Validation:** Hyperparameter tuning, feature selection, and alarm threshold selection are performed strictly via **5-fold `GroupKFold`** over the 80 development engines. The 20 held-out engines are evaluated only once at the end.
- **Strict Pipeline Containment:** All transformations (sensor filtering, standard scaling, imputation) are fitted strictly on the development training folds within scikit-learn `Pipeline` objects.

### Baseline Ladder
1. **Rung 0:** Mean RUL prediction / Never alarm (floor baseline).
2. **Rung 1:** Best fixed-interval replacement schedule at $K$ cycles (chosen on development folds).
3. **Rung 2:** Age-only linear model ($\text{RUL} = \text{typical life} - t$).
4. **Rung 3:** Regularized linear models (Ridge / Lasso) on instantaneous sensor readings.
5. **Rung 4:** Linear & Logistic models on trailing window summary features (rolling mean, rolling std, linear drift slope).
6. **Rung 5:** Non-linear tree ensembles (Random Forest, HistGradientBoosting).

### Evaluation Metrics
- **RUL Regression:** RMSE, MAE, and the **NASA Asymmetric Scoring Function** (penalizes overestimating RUL much more severely than underestimating RUL).
- **Alarm Classification:** PR-AUC, Precision, Recall, and Calibration Curves (reliability diagrams) at cost-optimal probability thresholds.
- **Cost Policy Simulation:** Total maintenance cost across cost ratios ($c_{\text{fail}} : c_{\text{waste}} \in \{2, 5, 10, 20, 50\}$) with bootstrap confidence intervals computed over test engines.

## 5. Getting Started

### 1. Environment Setup
Create a virtual environment and install dependencies:
```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/macOS:
source .venv/bin/activate

pip install -r requirements.txt
```

### 2. Verify Dataset Integrity
Verify that the raw FD001 dataset in `CMAPSSData/` is intact:
```bash
python scripts/verify_data.py
```

Expected output:
- **Train FD001:** 20,631 rows across 100 run-to-failure engines (lifetimes: 128 to 362 cycles).
- **Test FD001:** 13,096 rows across 100 truncated engines.
- **RUL FD001:** 100 ground-truth remaining lifetime values.

## 6. Planned Interactive Deliverables (`docs/`)

The final report is delivered as a client-side static web application hosted on GitHub Pages:
- **Interactive Cost-Curve Explorer:** Real-time sliders for alarm threshold and failure cost ratio ($c_{\text{fail}} : c_{\text{waste}}$) comparing policy savings against the fixed schedule.
- **Leakage Visualizer:** Side-by-side comparison illustrating how random row-level splitting artificially inflates predictive performance versus engine-level group splitting.
- **Error Inspector:** Interactive drill-down into engines with short/long lifespans and false alarm profiles.
